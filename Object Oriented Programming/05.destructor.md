# Destructor in Java

> In Java, there is **no traditional destructor** like in C++. Instead, Java relies on **Garbage Collection** to automatically manage memory. However, Java provides mechanisms like the `finalize()` method, `AutoCloseable` interface, and the `Cleaner` API for cleanup operations.

# What is a Destructor?

A **destructor** is a special method that is automatically called when an object is destroyed or goes out of scope. Its purpose is to release resources (memory, file handles, database connections, etc.) that the object may have acquired during its lifetime.

### Destructor in C++ vs Java

| Feature | C++ | Java |
|---|---|---|
| Destructor keyword | `~ClassName()` | No destructor keyword |
| Called automatically | Yes, when object goes out of scope | No direct equivalent |
| Memory management | Manual (developer's responsibility) | Automatic (Garbage Collector) |
| Resource cleanup | Destructor | `close()`, `try-with-resources`, `Cleaner` |
| Deterministic destruction | Yes | No (GC decides when to collect) |

In C++, a destructor is explicitly defined using the tilde (`~`) symbol:

```cpp
class Employee {
public:
    ~Employee() {
        // Cleanup code
        cout << "Employee object destroyed!" << endl;
    }
};
```

In Java, **there is no equivalent syntax**. Java uses the **Garbage Collector (GC)** to automatically reclaim memory when an object is no longer referenced.

# Garbage Collection in Java

Java uses an **automatic memory management** system called **Garbage Collection (GC)**. The Garbage Collector runs in the background and automatically deallocates memory occupied by objects that are no longer reachable or referenced.

### How It Works

1. When an object is created using `new`, memory is allocated on the **heap**.
2. The Garbage Collector periodically identifies objects that are no longer referenced by any part of the program.
3. These unreachable objects are marked for collection and their memory is reclaimed.

### Example

```java
class Employee {
    String name;

    Employee(String name) {
        this.name = name;
        System.out.println(name + " created.");
    }
}

class Main {
    public static void main(String[] args) {
        Employee e1 = new Employee("Raj");
        Employee e2 = new Employee("Rahul");

        // e1 is now eligible for garbage collection
        e1 = null;

        // Request garbage collection (not guaranteed to run immediately)
        System.gc();

        System.out.println("End of main method.");
    }
}
```

### Key Points

- The Garbage Collector runs **automatically** — the developer does not need to manually free memory.
- `System.gc()` is a **request** to run garbage collection, but it is **not guaranteed** to execute immediately.
- An object becomes eligible for GC when there are **no more references** pointing to it.
- The GC handles **memory deallocation only** — it does **not** close files, database connections, or network sockets.

# The `finalize()` Method

The `finalize()` method was Java's closest equivalent to a destructor. It is a method defined in the `Object` class that the Garbage Collector **may** call before reclaiming an object's memory.

### Syntax

```java
protected void finalize() throws Throwable {
    // Cleanup code
}
```

### Example

```java
class Employee {
    String name;

    Employee(String name) {
        this.name = name;
        System.out.println(name + " created.");
    }

    @Override
    protected void finalize() throws Throwable {
        System.out.println(name + " is being garbage collected!");
        super.finalize();
    }
}

class Main {
    public static void main(String[] args) {
        Employee e1 = new Employee("Raj");
        Employee e2 = new Employee("Rahul");

        // Making e1 eligible for garbage collection
        e1 = null;

        // Requesting garbage collection
        System.gc();

        System.out.println("End of main method.");
    }
}
```

**Possible Output:**

```
Raj created.
Rahul created.
Raj is being garbage collected!
End of main method.
```

> **Note:** The output order may vary because garbage collection is **non-deterministic** — the GC decides when to run.

---

## Why `finalize()` is Deprecated

The `finalize()` method was **deprecated in Java 9** and **removed for removal in Java 18**. Here are the reasons:

- **No guarantee of execution:** The JVM does **not guarantee** that `finalize()` will ever be called. If the GC never runs before the program terminates, finalization is skipped entirely.

- **Unpredictable timing:** Even if `finalize()` is called, the **timing is unpredictable**. Critical resources like file handles or database connections may remain open for an indefinite period.

- **Performance overhead:** Objects with `finalize()` methods require **extra processing** by the GC, slowing down garbage collection.

- **Resurrection risk:** Inside `finalize()`, the object can accidentally become reachable again (by assigning `this` to a static variable), preventing it from being collected. This is known as **object resurrection**.

- **Exception swallowing:** Any exception thrown inside `finalize()` is **silently ignored**, making debugging extremely difficult.

- **Single invocation:** The GC calls `finalize()` **at most once** per object, even if the object is resurrected and becomes unreachable again.

# Modern Alternative: `AutoCloseable` and `try-with-resources`

The recommended way to manage resource cleanup in Java is using the `AutoCloseable` interface along with the `try-with-resources` statement, introduced in **Java 7**.

### How It Works

1. A class implements the `AutoCloseable` (or `Closeable`) interface.
2. The class overrides the `close()` method with cleanup logic.
3. Objects are created inside a `try-with-resources` block.
4. The `close()` method is **automatically called** when the block finishes — even if an exception occurs.

### Example: File Resource Cleanup

```java
import java.io.*;

class FileManager implements AutoCloseable {
    private BufferedReader reader;

    public FileManager(String filePath) throws FileNotFoundException {
        this.reader = new BufferedReader(new FileReader(filePath));
        System.out.println("File opened: " + filePath);
    }

    public String readLine() throws IOException {
        return reader.readLine();
    }

    @Override
    public void close() throws IOException {
        reader.close();
        System.out.println("File closed. Resources released.");
    }
}

class Main {
    public static void main(String[] args) {
        // try-with-resources: close() is called automatically
        try (FileManager fm = new FileManager("data.txt")) {
            String line = fm.readLine();
            System.out.println("First line: " + line);
        } catch (IOException e) {
            System.out.println("Error: " + e.getMessage());
        }
        // At this point, close() has already been called automatically
        System.out.println("Outside try block — resource is already cleaned up.");
    }
}
```

### Example: Database Connection Cleanup

```java
import java.sql.*;

class DatabaseConnection implements AutoCloseable {
    private Connection connection;

    public DatabaseConnection(String url, String user, String password) throws SQLException {
        this.connection = DriverManager.getConnection(url, user, password);
        System.out.println("Database connected.");
    }

    public void executeQuery(String query) throws SQLException {
        Statement stmt = connection.createStatement();
        ResultSet rs = stmt.executeQuery(query);
        while (rs.next()) {
            System.out.println(rs.getString(1));
        }
    }

    @Override
    public void close() throws SQLException {
        if (connection != null && !connection.isClosed()) {
            connection.close();
            System.out.println("Database connection closed.");
        }
    }
}

class Main {
    public static void main(String[] args) {
        String url = "jdbc:mysql://localhost:3306/mydb";
        try (DatabaseConnection db = new DatabaseConnection(url, "root", "password")) {
            db.executeQuery("SELECT name FROM employees");
        } catch (SQLException e) {
            System.out.println("Database error: " + e.getMessage());
        }
        // Connection is automatically closed here
    }
}
```

### Example: Custom Resource Class

```java
class ResourceHolder implements AutoCloseable {
    private String resourceName;
    private boolean isOpen;

    public ResourceHolder(String name) {
        this.resourceName = name;
        this.isOpen = true;
        System.out.println("Resource acquired: " + resourceName);
    }

    public void use() {
        if (!isOpen) {
            throw new IllegalStateException("Resource is already closed!");
        }
        System.out.println("Using resource: " + resourceName);
    }

    @Override
    public void close() {
        if (isOpen) {
            isOpen = false;
            System.out.println("Resource released: " + resourceName);
        }
    }
}

class Main {
    public static void main(String[] args) {
        // Multiple resources in a single try-with-resources
        try (
            ResourceHolder r1 = new ResourceHolder("Connection");
            ResourceHolder r2 = new ResourceHolder("FileHandle")
        ) {
            r1.use();
            r2.use();
        }
        // Both resources are closed automatically in reverse order
        // Output:
        // Resource acquired: Connection
        // Resource acquired: FileHandle
        // Using resource: Connection
        // Using resource: FileHandle
        // Resource released: FileHandle
        // Resource released: Connection
    }
}
```

### Key Points

- Resources are closed in **reverse order** of their creation.
- The `close()` method is called even if an **exception** is thrown inside the `try` block.
- Multiple resources can be declared in a **single** `try-with-resources` statement.
- `Closeable` extends `AutoCloseable` — the difference is that `Closeable.close()` throws `IOException`, while `AutoCloseable.close()` throws `Exception`.

# The `Cleaner` API (Java 9+)

The `Cleaner` API was introduced in **Java 9** as a modern, safe replacement for `finalize()`. It allows cleanup actions to be registered for objects without the pitfalls of finalization.

### How It Works

1. A `Cleaner` instance is created.
2. A cleanup action (a `Runnable`) is registered with the `Cleaner` for a specific object.
3. When the object becomes **phantom reachable** (no longer accessible), the `Cleaner` runs the registered action.

### Example

```java
import java.lang.ref.Cleaner;

class Resource implements AutoCloseable {
    private static final Cleaner cleaner = Cleaner.create();

    // Cleaning action — must NOT reference the Resource object itself
    private static class CleaningAction implements Runnable {
        private final String resourceName;

        CleaningAction(String name) {
            this.resourceName = name;
        }

        @Override
        public void run() {
            System.out.println("Cleaner: Releasing " + resourceName);
        }
    }

    private final Cleaner.Cleanable cleanable;
    private final String name;

    public Resource(String name) {
        this.name = name;
        this.cleanable = cleaner.register(this, new CleaningAction(name));
        System.out.println("Resource created: " + name);
    }

    public void use() {
        System.out.println("Using resource: " + name);
    }

    @Override
    public void close() {
        System.out.println("Explicit close: " + name);
        cleanable.clean(); // Triggers cleanup and deregisters
    }
}

class Main {
    public static void main(String[] args) {
        // Preferred: explicit cleanup with try-with-resources
        try (Resource r = new Resource("DatabaseConn")) {
            r.use();
        }

        // Fallback: Cleaner handles cleanup if close() is not called
        Resource r2 = new Resource("FileHandle");
        r2.use();
        r2 = null;
        System.gc(); // Request GC — Cleaner may run the cleanup action
    }
}
```

### Key Points

- The cleaning action (`Runnable`) must **not** hold a reference to the object being cleaned. Otherwise, the object will never become unreachable and the cleaner will never run.
- `Cleaner` serves as a **safety net** — the primary cleanup mechanism should still be `try-with-resources` and `close()`.
- Calling `clean()` explicitly deregisters the action, preventing it from running twice.
- The `Cleaner` API is **thread-safe** and does not suffer from the pitfalls of `finalize()`.

# `AutoCloseable` vs `Closeable`

Both interfaces are used for resource management, but they have subtle differences:

| Feature | `AutoCloseable` | `Closeable` |
|---|---|---|
| Package | `java.lang` | `java.io` |
| Introduced in | Java 7 | Java 5 |
| `close()` throws | `Exception` | `IOException` |
| Idempotent requirement | Not required | `close()` must be idempotent (safe to call multiple times) |
| Use case | General-purpose resources | I/O-specific resources |
| Used with `try-with-resources` | Yes | Yes (since `Closeable` extends `AutoCloseable`) |

### Idempotent `close()` Example

```java
class SafeResource implements Closeable {
    private boolean closed = false;

    @Override
    public void close() throws IOException {
        if (!closed) {
            System.out.println("Releasing resource...");
            closed = true;
        }
        // Calling close() again does nothing — this is idempotent
    }
}
```

# Best Practices for Resource Cleanup

- **Always prefer `try-with-resources`** over manual `close()` calls in `finally` blocks. It is cleaner, safer, and handles exceptions properly.

- **Implement `AutoCloseable`** for any class that holds external resources (files, connections, streams, locks).

- **Never rely on `finalize()`** for cleanup. It is deprecated, unreliable, and has severe performance implications.

- **Use `Cleaner` as a safety net only.** The primary mechanism should always be explicit cleanup via `close()`.

- **Make `close()` idempotent.** Calling `close()` multiple times should not throw an error or cause side effects.

- **Release resources as soon as possible.** Don't keep files, connections, or streams open longer than necessary.

- **Log resource leaks in development.** Track unclosed resources during development to catch bugs early.

# Summary

| Mechanism | Reliability | When to Use |
|---|---|---|
| Garbage Collector | Automatic, non-deterministic | Memory deallocation (handled by JVM) |
| `finalize()` | Unreliable, deprecated | **Do not use** |
| `try-with-resources` + `AutoCloseable` | Deterministic, reliable | **Primary choice** for resource cleanup |
| `Cleaner` API | Safety net, non-deterministic | Backup in case `close()` is not called |
