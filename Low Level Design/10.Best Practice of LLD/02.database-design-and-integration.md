## 1. What is an ER Model?

The **Entity-Relationship (ER) Model** is a high-level conceptual data model used to define data elements and their relationships for a given system. It provides a structured visual representation through ER diagrams that depict:

- **Entities**: Real-world objects, actors, or business concepts that possess independent existence (e.g., `User`, `Transaction`, `Merchant`, `Invoice`).
- **Attributes**: Properties or characteristics that describe entities (e.g., a `User` entity has `user_id`, `name`, `email`, `phone`, `kyc_status`).
- **Relationships**: Associations or connections between two or more entities (e.g., a `User` initiates a `Payment`, a `Merchant` receives a `Payment`).

```
  ┌──────────────┐             1:N              ┌──────────────┐
  │     User     │ ───────────────────────────> │   Payment    │
  │ (Customer)   │       initiates / makes      │(Transaction) │
  └──────────────┘                              └──────┬───────┘
                                                       │
                                                       │ N:1
                                                       │ received by
                                                       ▼
  ┌──────────────┐             1:N              ┌──────────────┐
  │PaymentMethod │ <─────────────────────────── │   Merchant   │
  │(Card/UPI/NB) │         settled via          │ (Beneficiary)│
  └──────────────┘                              └──────────────┘
```

### Use-Case Example – Razorpay Payment System

- **Entities**: `User`, `Merchant`, `Payment`, `PaymentMethod`, `Invoice`.
- **Relationships**:
  - `User` $\rightarrow$ *makes* $\rightarrow$ `Payment` (One-to-Many: a user can initiate many payments).
  - `Merchant` $\rightarrow$ *receives* $\rightarrow$ `Payment` (One-to-Many: a merchant receives multiple customer payments).
  - `Payment` $\rightarrow$ *uses* $\rightarrow$ `PaymentMethod` (Many-to-One: multiple transactions use specific payment methods like UPI, Credit Card, Net Banking).

## 2. How to Design Tables from Requirements?

Once entities, attributes, and relationships are identified conceptually, the next phase is translating them into a physical relational database schema.

### Step-by-Step Translation Process

1. **Extract Entities from Requirements**: Identify all nouns and domain actors in the problem statement.
2. **Define Attributes for Each Entity**: Identify the properties and data types for each entity.
3. **Determine Primary and Foreign Keys**: Establish candidate keys, select a unique primary key (PK) for each table, and define foreign keys (FK) to enforce relational integrity.
4. **Normalize the Schema**: Apply normalization rules (**1NF**, **2NF**, **3NF**) to eliminate data redundancy, update anomalies, and insertion/deletion anomalies.
5. **Add Constraints and Indexes**: Define constraints (`NOT NULL`, `UNIQUE`, `CHECK`) and create indexes (B-Tree or Hash indexes) on high-cardinality foreign keys and frequently queried filter/sorting columns.

### Example – Razorpay Payment Flow Schema

**Requirement:** *A user pays a merchant through a payment gateway using a chosen payment method.*

```sql
-- 1. Users Table (Customer initiating transactions)
CREATE TABLE users (
    user_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE NOT NULL,
    phone VARCHAR(20) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 2. Merchants Table (Business receiving payouts)
CREATE TABLE merchants (
    merchant_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(150) NOT NULL,
    business_type VARCHAR(50) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 3. Payment Methods Table (UPI, Card, NetBanking providers)
CREATE TABLE payment_methods (
    method_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    type VARCHAR(50) NOT NULL,       -- e.g., 'UPI', 'CREDIT_CARD', 'NET_BANKING'
    provider VARCHAR(50) NOT NULL    -- e.g., 'HDFC', 'ICICI', 'NPCI'
);

-- 4. Payments Table (Transaction records linking user, merchant, and method)
CREATE TABLE payments (
    payment_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    merchant_id BIGINT NOT NULL,
    method_id BIGINT NOT NULL,
    amount DECIMAL(12, 2) NOT NULL,
    currency VARCHAR(3) DEFAULT 'INR',
    status VARCHAR(30) NOT NULL,     -- e.g., 'PENDING', 'SUCCESS', 'FAILED'
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_payments_user FOREIGN KEY (user_id) REFERENCES users(user_id),
    CONSTRAINT fk_payments_merchant FOREIGN KEY (merchant_id) REFERENCES merchants(merchant_id),
    CONSTRAINT fk_payments_method FOREIGN KEY (method_id) REFERENCES payment_methods(method_id)
);

-- Performance Indexes
CREATE INDEX idx_payments_user_id ON payments(user_id);
CREATE INDEX idx_payments_merchant_id ON payments(merchant_id);
CREATE INDEX idx_payments_status_timestamp ON payments(status, timestamp);
```

## 3. Mapping ER $\rightarrow$ Class Model

In object-oriented software engineering, application logic does not interact with raw SQL rows directly. Instead, relational schemas and ER models are mapped into an object-oriented domain model.

### Mapping Principles

| Database / ER Concept | Object-Oriented Class Concept |
| :--- | :--- |
| **Entity Table** | Java / Domain Class |
| **Column / Attribute** | Class Field / Instance Variable |
| **Primary Key** | Identifier Field (`id`) |
| **Foreign Key (1:N)** | Object reference (`User user`) or Collection (`List<Payment> payments`) |
| **Join Table (M:N)** | Bidirectional Collections (`Set<Role> roles`) |

### Example – Razorpay Class Model (Java)

```java
import java.util.List;

// User Domain Model
public class User {
    private Long id;
    private String name;
    private String email;
    private String phone;
    private List<Payment> payments; // 1:N relationship with Payment

    public User() {}

    public User(Long id, String name, String email, String phone) {
        this.id = id;
        this.name = name;
        this.email = email;
        this.phone = phone;
    }

    // Getters and Setters
    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
    public String getPhone() { return phone; }
    public void setPhone(String phone) { this.phone = phone; }
    public List<Payment> getPayments() { return payments; }
    public void setPayments(List<Payment> payments) { this.payments = payments; }
}
```

```java
import java.time.LocalDateTime;

// Payment Domain Model
public class Payment {
    private Long id;
    private User user;             // N:1 association to User
    private Merchant merchant;     // N:1 association to Merchant
    private Double amount;
    private String method;
    private String status;
    private LocalDateTime timestamp;

    public Payment() {}

    public Payment(Long id, User user, Merchant merchant, Double amount, String method) {
        this.id = id;
        this.user = user;
        this.merchant = merchant;
        this.amount = amount;
        this.method = method;
        this.timestamp = LocalDateTime.now();
    }

    // Getters and Setters
    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public User getUser() { return user; }
    public void setUser(User user) { this.user = user; }
    public Merchant getMerchant() { return merchant; }
    public void setMerchant(Merchant merchant) { this.merchant = merchant; }
    public Double getAmount() { return amount; }
    public void setAmount(Double amount) { this.amount = amount; }
    public String getMethod() { return method; }
    public void setMethod(String method) { this.method = method; }
    public String getStatus() { return status; }
    public void setStatus(String status) { this.status = status; }
    public LocalDateTime getTimestamp() { return timestamp; }
    public void setTimestamp(LocalDateTime timestamp) { this.timestamp = timestamp; }
}
```

## 4. What is DAO (Data Access Object)?

The **Data Access Object (DAO)** is a structural design pattern that abstracts and encapsulates all access to the underlying data source (e.g., relational databases, NoSQL datastores, or file systems). 

The DAO manages the connection with the data source to obtain and store data, completely decoupling persistence logic from business and domain services.

```
  ┌──────────────────┐
  │ Business Service │ (e.g., PaymentProcessingService)
  └────────┬─────────┘
           │ Calls domain operations
           ▼
  ┌──────────────────┐
  │  DAO Interface   │ (e.g., PaymentDAO)
  └────────┬─────────┘
           │ Implemented by
           ▼
  ┌──────────────────┐
  │  DAO SQL Impl    │ (JDBC / Hibernate / Raw SQL Queries)
  └────────┬─────────┘
           │ Executes queries
           ▼
  ┌──────────────────┐
  │ Relational DB    │ (PostgreSQL / MySQL)
  └──────────────────┘
```

### Benefits of DAO Pattern

- **Loose Coupling**: Business logic is insulated from database-specific syntax (e.g., swapping MySQL for PostgreSQL requires changing only the DAO implementation).
- **Testability**: Services can be easily unit-tested by mocking the DAO interface without spinning up live database instances.
- **Separation of Concerns**: SQL queries, connection pooling, and result set mapping remain contained within persistence classes.

### Example – Java DAO Interface

```java
import java.util.List;

public interface PaymentDAO {
    Payment getPaymentById(Long id);
    List<Payment> getPaymentsByUser(Long userId);
    void save(Payment payment);
    void updateStatus(Long paymentId, String status);
    void delete(Long id);
}
```

## 5. What is the Repository Pattern?

The **Repository pattern** is an architectural pattern that sits between the domain and data mapping layers, acting like an **in-memory collection of domain objects**.

While a DAO is centered around database operations (CRUD, table access, and SQL queries), a Repository is centered around the **domain model**, providing a higher-level collection abstraction. In modern frameworks like Spring Boot, the Repository pattern is commonly implemented via **Spring Data JPA**.

### DAO vs. Repository Comparison

| Feature / Dimension | DAO (Data Access Object) | Repository |
| :--- | :--- | :--- |
| **Primary Focus** | Focused on database storage & persistence operations. | Focused on managing a collection of domain objects. |
| **Centricity** | More database-centric and table-centric. | More domain-driven and business-centric (DDD). |
| **SQL Awareness** | Often contains explicit SQL queries, JDBC mappings, or named queries. | Hides persistence mechanisms completely behind collection semantics. |
| **Implementation** | Typically manually written using JDBC or EntityManager. | Often auto-generated by frameworks (e.g., `JpaRepository` proxy). |
| **Abstraction Level** | Low-level data access abstraction. | Higher-level domain collection abstraction. |

### Example – Spring Data JPA Repository

```java
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.stereotype.Repository;
import java.util.List;

@Repository
public interface PaymentRepository extends JpaRepository<Payment, Long> {
    // Spring Data automatically derives the query from the method signature
    List<Payment> findByUserId(Long userId);

    List<Payment> findByMerchantIdAndStatus(Long merchantId, String status);
}
```

## 6. Real-World Enhancements and Practices

Building production-grade payment gateways like Razorpay requires scaling beyond basic table definitions and repositories. The following industry practices harden database architecture against failure, load, and security risks:

### 1. Read/Write Optimization
- **Read Replicas**: Direct all write operations (`INSERT`, `UPDATE`, `DELETE`) to a primary master database, while distributing read queries (`SELECT`) across multiple read replicas.
- **Batch Processing**: Use JDBC batch updates for high-volume transactions to minimize network roundtrips between the application server and the database.

### 2. Caching Layer
- Place an in-memory cache (**Redis** or **Memcached**) in front of the database for frequently read, low-volatility data (e.g., merchant profiles, active payment method configurations, exchange rates).
- Implement cache-aside or write-through caching strategies with strict TTLs (Time-To-Live) to avoid serving stale data.

### 3. Auditing and Logging
- **Immutable Transaction Logs**: Every financial ledger mutation must be recorded in an immutable append-only audit log table.
- **Change Data Capture (CDC)**: Use tools like **Debezium** and **Apache Kafka** to stream row-level database changes asynchronously for analytics, fraud detection, and reconciliation without impacting payment throughput.

### 4. Security Best Practices
- **Field-Level Encryption**: Encrypt sensitive data (cardholder numbers, bank account details, PII) at rest using AES-256 before persisting.
- **Role-Based Access Control (RBAC)**: Grant strict least-privilege permissions to database users (e.g., application service users cannot drop tables or alter schemas).
- **Parameterized Queries**: Always use prepared statements and ORM parameter bindings to eliminate SQL injection vulnerabilities.

### 5. Schema Versioning & Migrations
- Use automated database migration tools like **Flyway** or **Liquibase**.
- Check SQL migration scripts (`V1__init_schema.sql`, `V2__add_currency_column.sql`) into version control to ensure consistent schema deployments across development, staging, and production environments.

### 6. Testing and Monitoring
- **Integration Testing**: Use **Testcontainers** to run automated integration tests against real containerized PostgreSQL/MySQL instances during CI builds.
- **Telemetry & Monitoring**: Track slow query logs, connection pool utilization (HikariCP metrics), lock contention, and query latency using **Prometheus**, **Grafana**, and database APM agents.

## Summary

Sound database design and integration in Low-Level Design bridges abstract business logic and concrete data persistence. By understanding the progression from conceptual ER models to normalized schemas, mapping to object-oriented domain models, and adopting established patterns like DAO and Repository, engineering teams can build scalable, high-throughput financial systems.

| Architectural Layer | Core Responsibility | Key Pattern / Technology |
| :--- | :--- | :--- |
| **Conceptual Layer** | Define business entities, attributes, and cardinality | ER Diagram Modeling |
| **Relational Schema** | Enforce normalization, keys, constraints, and indexes | SQL DDL, 3NF Normalization |
| **Domain Layer** | Encapsulate business logic in object-oriented classes | Java POJO / Domain Entity |
| **Persistence Abstraction** | Decouple data access logic from business services | DAO Pattern, Repository Pattern |
| **Infrastructure & Scale** | Ensure performance, durability, auditability, and security | Read Replicas, Redis, CDC, Flyway |
