## 1. What Are APIs? Things to Keep in Mind While Designing Them

An **Application Programming Interface (API)** is a formal contract that allows two software components to interact. It explicitly defines what data can be exchanged, how it can be accessed, and under what operational constraints. 

API design directly impacts the developer experience (DX), system extensibility, backward compatibility, and the overarching security posture of an organization. Designing APIs is not merely about exposing database tables as endpoints—it is about creating an intuitive, consistent, and dependable abstraction layer.

### Key Design Considerations

| Consideration | Description & Best Practice |
| :--- | :--- |
| **Clarity** | Use intuitive, self-describing, and pluralized resource names (e.g., `/api/v1/users`, `/api/v1/payments`) instead of RPC-style verbs (e.g., avoid `/getUser` or `/executePayment`). |
| **Consistency** | Establish uniform naming conventions across all endpoints (e.g., `camelCase` or `kebab-case`), standardized error response bodies, and standardized HTTP method usages. |
| **Predictability** | Avoid unexpected side effects. Given the same request input and system state, the API must always produce predictable and deterministic output. |
| **Minimalism** | Expose only what the client truly requires. Avoid leaking internal database fields, internal IDs, or huge payloads that bloat network bandwidth. |
| **Statelessness** | Adhere to RESTful statelessness. Each request from any client must contain all necessary authentication, authorization, and state data needed to service the request without relying on server-side sessions. |

## 2. API Lifecycle Across Teams

APIs are collaborative contracts that span multiple organizational boundaries—from backend engineers and frontend consumers to DevOps, QA automation, and product managers. A structured API lifecycle guarantees quality, prevents breaking changes, and maintains visibility at every stage.

```
  ┌───────────┐      ┌─────────────┐      ┌─────────────┐      ┌────────────┐
  │  Design   │ ───> │ Development │ ───> │   Testing   │ ───> │ Deployment │
  │ (OpenAPI) │      │ (Spec-First)│      │  (Contract) │      │ (Canary/BG)│
  └───────────┘      └─────────────┘      └─────────────┘      └─────┬──────┘
                                                                     │
  ┌─────────────┐    ┌─────────────┐      ┌─────────────┐            │
  │ Deprecation │ <─ │ Versioning  │ <─── │ Monitoring  │ <──────────┘
  │ (Sunsetting)│    │(Maintenance)│      │(SLAs/Metrics│
  └─────────────┘    └─────────────┘      └─────────────┘
```

### Stages of the API Lifecycle

1. **Design**: Define contracts before writing code using specification standards like **OpenAPI (Swagger)**. Detail all endpoints, query parameters, payload schemas, and anticipated HTTP status codes.
2. **Development**: Implement the API against the approved specification. Utilize code reviews, static linters, and version control branches to maintain standards.
3. **Testing**: Execute automated unit tests, integration tests, and **contract tests** (e.g., Pact). Utilize mocks and stubs to allow frontend and consumer teams to develop concurrently without waiting for backend deployment.
4. **Deployment**: Ship API updates through automated CI/CD pipelines. Utilize zero-downtime deployment patterns such as **Canary releases**, **Blue-Green deployments**, or **feature toggles** to control blast radius.
5. **Monitoring**: Track real-time telemetry including request latency (P95/P99), error rates (4xx/5xx ratios), throughput, and uptime using tools like Prometheus, Grafana, Datadog, or Postman Monitor.
6. **Versioning / Maintenance**: Incrementally introduce non-breaking improvements while maintaining backward compatibility for all active clients.
7. **Deprecation**: Formally sunset outdated versions by communicating sunset timelines, emitting deprecation headers (`Sunset`, `Deprecation`), and offering migration guides.

## 3. Advanced REST Principles & Sensitive Operations

True REST architectural style goes beyond mapping CRUD operations to HTTP verbs. Building enterprise APIs requires implementing advanced REST constraints and treating security-sensitive workflows with defense-in-depth safeguards.

### Advanced REST Guidelines

- **HATEOAS (Hypermedia as the Engine of Application State)**: Provide hypermedia links within responses to guide clients on possible subsequent actions without requiring hardcoded URLs on the client side:
  ```json
  {
    "orderId": "ord_89211",
    "status": "PENDING_PAYMENT",
    "amount": 149.99,
    "_links": {
      "self": { "href": "/api/v1/orders/ord_89211" },
      "payment": { "href": "/api/v1/orders/ord_89211/payments", "method": "POST" },
      "cancel": { "href": "/api/v1/orders/ord_89211/cancel", "method": "PUT" }
    }
  }
  ```
- **Idempotency**: Ensure safe retries by making operations idempotent:
  - `GET`, `HEAD`, `OPTIONS`: Naturally safe and read-only.
  - `PUT`, `DELETE`: Inherently idempotent; executing them multiple times results in the same state.
  - `POST`: Non-idempotent by default. For financial and ordering systems, implement **Idempotency Keys** (e.g., `Idempotency-Key: <UUID>`) in request headers to safely deduplicate duplicate requests caused by network timeouts.
- **Partial Updates via PATCH**: Use `PATCH` with JSON Merge Patch or JSON Patch formats to update specific fields rather than forcing clients to submit the full resource representation using `PUT`.
- **Schema Validation**: Validate incoming payloads against strict JSON Schemas or DTO annotations before requests reach domain logic.

### Handling Sensitive Operations

Operations involving funds transfers, account recovery, password changes, or role elevation require specialized safeguards:

- **Two-Step Confirmation**: Require multi-factor authentication (MFA), one-time passwords (OTP), or explicit email verification before committing high-risk mutations.
- **Appropriate Status Codes**: Return `401 Unauthorized` for missing/invalid authentication credentials and `403 Forbidden` for authenticated callers who lack necessary permissions. Never swallow authentication errors into generic `500 Internal Server Error` responses.
- **Payload & Parameter Security**: Never expose sensitive data (passwords, tokens, API keys, personally identifiable information) in URL query parameters, as URLs are logged in web server logs, browser histories, and proxy caches. Pass sensitive inputs in encrypted request bodies over TLS.

## 4. DTO Patterns – Designing Contracts

**Data Transfer Objects (DTOs)** are plain objects designed exclusively to carry data between subsystems. In API design, DTOs decouple external API contracts from internal domain models and persistence entities (e.g., JPA/Hibernate entities).

```
   Client Request
        │
        ▼
   [ UserCreateRequestDTO ]  ── (Validation: @NotNull, @Email)
        │
        ▼ (Mapping via MapStruct / ModelMapper)
   [ User Domain Entity ]    ── (Business Rules & Persistence)
        │
        ▼ (Mapping)
   [ UserResponseDTO ]       ── (Encapsulation: Omit passwordHash, internal IDs)
        │
        ▼
   Client Response
```

### Best Practices for DTOs

| Best Practice | Description |
| :--- | :--- |
| **Declarative Validation** | Annotate DTOs with validation constraints (e.g., `@NotNull`, `@Email`, `@Size(min = 8)`) so that invalid payloads are rejected at the controller boundary. |
| **Strict Encapsulation** | Never expose raw database entities. Entities contain internal columns (e.g., `password_hash`, `tenant_id`, `version`, soft-delete flags) that must never leak to API consumers. |
| **Separate Request and Response DTOs** | Do not reuse a single object for both incoming and outgoing payloads. Request DTOs require fields clients submit; Response DTOs contain server-generated metadata (`id`, `createdAt`, `status`). |
| **Immutable Contracts** | Treat published DTO fields as immutable contracts. Any change to field names or data types must be treated as a breaking change requiring versioning. |

## 5. Error Handling

A robust error-handling architecture provides clear, actionable feedback to clients while preventing stack traces or database schema details from leaking into public responses.

### Recommended Error Response Structure

All error responses across the entire API suite should follow a uniform, machine-readable format (such as RFC 7807 Problem Details or custom company-wide standards):

```json
{
  "timestamp": "2025-07-29T10:23:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Missing required field: email",
  "path": "/api/users"
}
```

For validation failures with multiple field errors, extend the structure with an `errors` collection:

```json
{
  "timestamp": "2025-07-29T10:23:00Z",
  "status": 422,
  "error": "Unprocessable Entity",
  "message": "Validation failed for request payload",
  "path": "/api/users",
  "errors": [
    { "field": "email", "reason": "Must be a well-formed email address" },
    { "field": "age", "reason": "Must be greater than or equal to 18" }
  ]
}
```

### HTTP Status Code Guidelines

| Category | Code & Name | Appropriate Usage |
| :--- | :--- | :--- |
| **2xx Success** | `200 OK` | Standard response for successful synchronous operations (`GET`, `PUT`, `PATCH`). |
| | `201 Created` | Successful creation of a resource (`POST`); should return `Location` header. |
| | `202 Accepted` | Request accepted for asynchronous/queued processing. |
| | `204 No Content` | Successful operation returning no body content (commonly used for `DELETE`). |
| **4xx Client Error** | `400 Bad Request` | Malformed JSON syntax or missing mandatory request elements. |
| | `401 Unauthorized` | Missing, expired, or invalid authentication token. |
| | `403 Forbidden` | Authenticated client lacks required permissions to access resource. |
| | `404 Not Found` | Target resource does not exist. |
| | `409 Conflict` | Conflict with current state (e.g., duplicate unique email or optimistic lock failure). |
| | `422 Unprocessable` | Well-formed JSON syntax, but semantic domain validation failed. |
| | `429 Too Many Requests` | Client exceeded allotted rate limit. |
| **5xx Server Error** | `500 Internal Error` | Unexpected unhandled server exception. |
| | `502 Bad Gateway` | Upstream microservice or dependency returned an invalid response. |
| | `503 Service Unavailable` | Service temporarily overloaded, undergoing maintenance, or circuit breaker open. |
| | `504 Gateway Timeout` | Upstream service failed to respond within configured timeout window. |

## 6. Versioning

APIs inevitably evolve as requirements change. Versioning enables organizations to introduce breaking modifications without disrupting existing client integrations.

### Common Versioning Strategies

| Strategy | Syntax Example | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **URI Versioning** | `/api/v1/users`<br />`/api/v2/users` | Most explicit; easiest to route, test, and cache in CDNs and browser caches. | Clutters URI space; can lead to URI proliferation. |
| **Header Versioning** | `X-API-Version: 1`<br />`X-API-Version: 2` | Keeps URLs clean; allows fine-grained method routing. | Harder to test directly in standard browser bars; requires custom routing proxies. |
| **Media Type Versioning** (Content Negotiation) | `Accept: application/vnd.company.v1+json` | Pure REST compliance; treats versions as representations. | Complex client configurations; difficult to inspect and test quickly. |

### Versioning Best Practices

- **Reserve New Versions for Breaking Changes Only**: Additive changes (e.g., adding an optional field to a response) should be backward-compatible and not trigger a version bump.
- **Maintain Deprecation Windows**: Support previous API versions for a defined period (e.g., 6–12 months) before decommissioning.
- **Publish Migration Guides**: Provide clear changelogs, diffs, and migration playbooks to assist consumer teams in upgrading seamlessly.

## 7. Filtering, Sorting, and Pagination

Exposing endpoints that return unbounded collections is a critical performance hazard. Large datasets can overwhelm network bandwidth, exhaust JVM heap space, and lock database connections.

### Example Query Parameters

```http
GET /api/v1/orders?page=2&limit=50&sort=created_at&order=desc&status=active&type=premium HTTP/1.1
Host: api.example.com
```

- **Pagination**: `?page=2&limit=50` (or cursor-based: `?cursor=eyJpZCI6MTIzfQ==&limit=50`).
- **Sorting**: `?sort=created_at&order=desc` (supports comma-separated fields: `?sort=-created_at,+price`).
- **Filtering**: `?status=active&type=premium` (supports operators: `?price_gte=100&price_lte=500`).

### Standard Paginated Response Format

Encapsulate collection responses within an envelope containing data and navigational metadata:

```json
{
  "data": [
    {
      "id": "usr_101",
      "name": "Alice Johnson",
      "status": "active"
    },
    {
      "id": "usr_102",
      "name": "Bob Smith",
      "status": "active"
    }
  ],
  "page": 2,
  "limit": 50,
  "totalItems": 320,
  "totalPages": 7
}
```

> [!TIP]
> **Offset vs. Cursor-Based Pagination:**
> - **Offset Pagination** (`page`, `limit`) is straightforward for UI pagination bars, but suffers performance degradation on large offsets (`OFFSET 100000`) and can skip/duplicate rows during concurrent writes.
> - **Cursor Pagination** (`after`, `limit`) uses an indexed pointer (such as an ID or timestamp) to achieve constant $O(1)$ database seek performance, ideal for infinite-scroll mobile feeds and high-velocity feeds.

## 8. API Security Considerations, Throttling, and Rate Limiting

APIs must be architected with **secure by default** principles. A single unshielded API endpoint can result in credential stuffing, distributed denial of service, or massive data exfiltration.

### Security Best Practices

1. **Authentication**: Verify client identity using industry standards:
   - **OAuth 2.0 / OpenID Connect**: For delegated user authorization and SSO.
   - **JWT (JSON Web Tokens)**: For stateless, cryptographically signed bearer tokens.
   - **API Keys**: For server-to-server machine integrations, rotated on regular cadences.
2. **Authorization**: Enforce granular access boundaries:
   - **RBAC (Role-Based Access Control)**: Restrict actions by predefined roles (e.g., `ADMIN`, `USER`, `BILLING_MANAGER`).
   - **PBAC (Policy/Permission-Based Access Control)**: Fine-grained permissions evaluated dynamically against resource ownership.
3. **Input Validation & Sanitization**: Sanitize and strictly type-check all incoming request payloads to prevent SQL Injection (SQLi), Cross-Site Scripting (XSS), and Server-Side Request Forgery (SSRF).
4. **HTTPS Everywhere**: Terminate TLS 1.2+ across all external and internal API gateways, ensuring end-to-end data transit encryption.

---

### Throttling and Rate Limiting

Rate limiting protects downstream infrastructure against intentional denial-of-service attacks, scraping, and unintentional runaway client retry loops.

- **Rate Limits**: Cap requests allowed within a defined temporal window (e.g., 100 requests per minute per IP or API key).
- **Throttling**: Dynamically delay or queue requests that exceed capacity thresholds rather than immediately dropping them.
- **Quota Enforcement**: Apply business-tier limits (e.g., Free Tier: 1,000 calls/day; Enterprise Tier: 1,000,000 calls/day).

#### Standard HTTP 429 Response

When a client breaches rate thresholds, return `HTTP 429 Too Many Requests` accompanied by the `Retry-After` header indicating the required wait duration in seconds:

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 60
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1722248640

{
  "error": "Too many requests. Please retry after 60 seconds."
}
```

## Summary

Thoughtfully designed APIs act as stable foundations for digital products, enabling scalable innovation and collaboration across engineering organizations. By implementing clear contracts, rigorous versioning, and defense-in-depth security, systems remain maintainable and resilient under high enterprise workloads.

| Architectural Dimension | Recommended Best Practice | Common Pitfall to Avoid |
| :--- | :--- | :--- |
| **API Contract** | DTO pattern with input validation annotations | Exposing raw database/ORM entities to clients |
| **Resource Naming** | Noun-based, pluralized, predictable URIs | Verb-based, RPC-style endpoints (`/fetchUsers`) |
| **State Management** | Completely stateless; token-based authentication | Server-bound HTTP sessions in distributed backends |
| **Error Handling** | Uniform, machine-readable JSON structure with RFC codes | Inconsistent errors or returning HTTP 200 with error payloads |
| **Lifecycle & Deprecation** | Automated contract testing; clear sunset windows | Silently introducing breaking changes to active endpoints |
| **Large Query Result Sets** | Enforced pagination (offset or cursor) with bounds | Returning unbounded collections that crash server memory |
| **Traffic Governance** | Rate limiting, token buckets, and HTTP 429 backoff | Unmetered public endpoints exposed to abuse and DDoS |
