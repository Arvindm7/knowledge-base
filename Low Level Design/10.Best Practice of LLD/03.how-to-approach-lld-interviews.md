## Introduction

Low-Level Design (LLD) interviews can be challenging but are a crucial part of software engineering interviews for mid, senior, and staff roles. Unlike High-Level Design (HLD) interviews—which focus on distributed systems, microservices, caches, and database partitions—LLD interviews assess your ability to translate ambiguous business requirements into clean, modular, extensible, and testable object-oriented code.

This guide serves as a comprehensive, step-by-step roadmap to approaching an LLD interview, addressing common doubts, and providing actionable strategies to succeed. By following this 9-step framework, you will learn how to break down complex problems, structure class interactions cleanly, and communicate your design decisions clearly.

## Step 1: Clarify Requirements

In any LLD interview, the first step is always to clarify requirements. Never start coding or drawing class diagrams immediately. Jumping prematurely into design risks solving the wrong problem, introducing unnecessary complexity, or missing implicit constraints.

Spend the first 5–8 minutes scoping the system collaboratively with the interviewer by dividing requirements into three categories:

### A. Functional Requirements
Functional requirements define the core capabilities, behaviors, and business processes the system must execute. They directly answer: *What should the system do?*

- **E-commerce System Example**:
  - Browse and search products with filters.
  - Manage a shopping cart (add, update quantity, remove).
  - Process checkout and payments via multiple payment gateways.
- **Parking Lot System Example**:
  - Park a vehicle into an appropriately sized slot (Compact, Large, Motorcycle).
  - Generate and assign a parking ticket.
  - Calculate parking fees upon exit and release the slot.

> [!TIP]
> **Key Strategy**: Always confirm the boundaries of what is **in-scope** versus **out-of-scope** for the 45-minute discussion.

### B. Non-Functional Requirements
Non-functional requirements specify operational qualities, constraints, and system characteristics rather than specific functional features. They answer: *How well must the system perform?*

| Non-Functional Metric | Architectural Focus |
| :--- | :--- |
| **Scalability** | Can the class model and memory structures support millions of objects or concurrent threads without memory leaks? |
| **Latency** | Are critical read/write paths optimized with fast lookups ($O(1)$ hash maps or indexed collections)? |
| **Availability & Fault Tolerance** | How gracefully does the system recover if an external payment gateway fails? |
| **Security & Auditing** | Are sensitive attributes (passwords, payment tokens) encapsulated and protected from unauthorized access? |

### C. Hero Use Cases
Hero use cases (or primary use cases) represent the most critical, frequent, and high-impact workflows through the system. Focusing on hero use cases ensures that the core domain architecture is bulletproof before addressing peripheral requirements.

- **E-commerce Example**: A customer searches for a product, adds it to the cart, applies a discount code, and completes payment.
- **Parking Lot Example**: A driver arrives at an entry gate, receives a ticket for an allocated spot, parks, returns later, pays the ticket fee, and exits.

## Step 2: Identify Core Entities

Once requirements and use cases are established, identify the fundamental domain entities. Core entities are the primary business objects that form the foundational building blocks of your object-oriented design.

### A. Define All Core Domain Entities
Entities are the nouns in your requirements that have distinct identities, lifecycles, and responsibilities.

- **Movie Streaming Service**: `User`, `Movie`, `VideoAsset`, `Subscription`, `ViewingSession`.
- **Parking Lot System**: `Vehicle`, `ParkingSlot`, `Ticket`, `Payment`, `EntryGate`, `ExitGate`.

### B. Include Attributes, Responsibilities, and Relationships
For each identified entity, define:
1. **Attributes**: Data properties that define entity state (e.g., `User` has `userId`, `name`, `email`, `subscriptionTier`).
2. **Responsibilities**: Actions and business invariants the entity enforces (e.g., `ParkingSlot` tracks its occupancy state and verifies vehicle compatibility).
3. **Relationships**: How entities connect structurally (Association, Aggregation, Composition, Inheritance).

### C. Mention Auxiliary / Supporting Entities
Supporting entities assist core entities by managing ancillary tasks, enumeration states, or contextual data:
- **Streaming System**: `Genre`, `SubtitleTrack`, `QualityProfile` (4K/1080p).
- **Parking Lot System**: `VehicleType` (Enum: `CAR`, `BIKE`, `TRUCK`), `SlotType`, `PricingStrategy`.

## Step 3: Visualize Interaction Flow

Software systems are dynamic. After defining static entities, map out how components communicate during runtime to ensure data moves seamlessly between users, domain services, and external integrations.

```
  Actor (User)        Controller / Gateway           Service Layer              Repository / DB
       │                        │                          │                           │
       │─── 1. submitOrder() ──>│                          │                           │
       │                        │── 2. processCheckout() ─>│                           │
       │                        │                          │── 3. checkInventory() ───>│
       │                        │                          │<─ 4. inventoryConfirmed ──│
       │                        │                          │                           │
       │                        │                          │── 5. chargePayment() ────┐ (External API)
       │                        │                          │<─ 6. paymentSuccess ─────┘
       │                        │                          │                           │
       │                        │                          │── 7. saveOrder() ────────>│
       │                        │<── 8. orderPlaced ───────│                           │
       │<── 9. HTTP 201 ────────│                          │                           │
```

### Key Areas to Outline

1. **Who Interacts with Whom**:
   - Trace the exact sequence: Client $\rightarrow$ Controller $\rightarrow$ Service $\rightarrow$ External Gateway / Repository.
2. **Sequence Flows & Flowcharts**:
   - Distinguish between **synchronous request-response flows** (checking slot availability) and **asynchronous background jobs** (sending invoice receipt emails).
3. **System Interactions with Users**:
   - Map user actions (clicking checkout, scanning tickets) to system state transitions and user feedback.
4. **External System Calls**:
   - Explicitly account for third-party integrations (payment processors, SMS gateways).
   - Design defensively: define timeouts, retries, and fallback behaviors in case external systems fail or lag.

## Step 4: Define Class Structures and Relationships

Translate domain entities into a cohesive, maintainable codebase architecture by applying Object-Oriented Programming (OOP) and SOLID design principles.

### A. Apply OOP and SOLID Principles

| SOLID Principle | Meaning | Application in LLD |
| :--- | :--- | :--- |
| **S - Single Responsibility** | A class should have only one reason to change. | Separate invoice calculation (`FeeCalculator`) from payment processing (`PaymentService`). |
| **O - Open / Closed** | Open for extension, closed for modification. | Support new vehicle types or pricing schemes via polymorphic strategies without editing existing classes. |
| **L - Liskov Substitution** | Subtypes must be substitutable for their base types. | Any subclass of `ParkingSlot` (e.g., `EVChargingSlot`) must honor the base slot interface contract without breaking callers. |
| **I - Interface Segregation** | Clients should not be forced to depend on methods they do not use. | Prefer focused interfaces (`PrintableTicket`, `Payable`) over monolithic interfaces. |
| **D - Dependency Inversion** | High-level modules should depend on abstractions, not concrete details. | Services inject interfaces (`PaymentProcessor`) rather than hardcoding `StripeClient`. |

### B. Layered Architectural Decomposition

Structure code into clean architectural tiers:
- **Controller Layer**: Handles HTTP/RPC requests, extracts parameters, and delegates to services.
- **Service Layer**: Contains core domain workflows and business rules.
- **Repository / DAO Layer**: Encapsulates persistence, querying, and data mapping.
- **Domain Models**: Plain objects encapsulating business state and core domain logic.

### C. Design for Loose Coupling and High Cohesion
- **Loose Coupling**: Keep class dependencies minimal and abstraction-based so modifying one component doesn't ripple across the system.
- **High Cohesion**: Ensure methods within a class closely relate to the core intent of that class.

## Step 5: Define Core Use Cases and Methods

Detail the major operations of your system by specifying method signatures, input/output data models, and collaborative interactions.

### A. For Every Major Feature, Define
- **Method Responsibilities**: Explicit function name, parameters, return types, and exceptions thrown.
- **I/O Models (DTOs)**: Request and response objects that isolate domain models from external callers.
- **Collaborating Classes**: Which services, strategies, or repositories coordinate to fulfill the request.
- **Transaction Boundaries**: Where transactions begin, commit, or roll back upon failure.

### B. Categorizing Use Cases

```
                                  System Use Cases
                                         │
        ┌────────────────────────────────┼────────────────────────────────┐
        ▼                                ▼                                ▼
  [ CRUD Operations ]          [ Real-Time Flows ]             [ Background Tasks ]
  - Create User                - Concurrency locks             - Asynchronous email
  - Fetch Catalog              - Seat / Slot reservation       - Billing reconciliations
  - Update Order Status        - Dynamic pricing updates       - Log purging
```

1. **CRUD Operations**: Fundamental read/write queries.
2. **Real-Time Flows**: Operations requiring instantaneous, thread-safe updates (e.g., slot locking, real-time seat assignment).
3. **Background Tasks**: Asynchronous tasks offloaded to thread pools or message brokers (e.g., notification delivery, metric aggregation).

## Step 6: Apply Design Patterns

Design patterns provide battle-tested blueprints for recurring structural and behavioral challenges. Never force patterns arbitrarily; always justify *why* a particular pattern fits the specific problem constraint.

### Common Design Patterns in LLD Interviews

| Pattern Category | Pattern | Ideal Use Case in LLD |
| :--- | :--- | :--- |
| **Creational** | **Factory / Abstract Factory** | Instantiating different vehicle types, payment methods, or notification channels based on runtime parameters. |
| | **Builder** | Constructing complex entities with multiple optional attributes (e.g., `SearchFilter`, `Invoice`). |
| | **Singleton** | Managing centralized configuration managers, hardware lock managers, or connection pools. |
| **Structural** | **Adapter** | Normalizing disparate external third-party APIs (e.g., adapting PayPal and Stripe SDKs into a unified interface). |
| | **Decorator** | Dynamically attaching add-ons (e.g., adding gift wrapping or priority shipping to an order). |
| | **Composite** | Managing hierarchical tree structures (e.g., file systems, organization charts, bundled products). |
| **Behavioral** | **Strategy** | Swapping algorithms dynamically at runtime (e.g., dynamic pricing strategies, discount calculations, slot allocation algorithms). |
| | **Observer** | Notifying multiple dependent subsystems on state change (e.g., notifying analytics, inventory, and SMS services on order placement). |
| | **State** | Managing complex entity lifecycles (e.g., `VendingMachine` states: `Idle`, `HasCoin`, `Dispensing`, `SoldOut`). |
| | **Command** | Encapsulating requests as objects to support undo/redo or execution queues. |

### Clean Code Practices
- **Self-Documenting Naming**: Name variables, methods, and classes after domain concepts (`allocateNearestSlot()`, not `doWork()`).
- **Consistent Formatting & Modularity**: Keep methods small (< 20 lines) and focused on a single task.
- **Minimal Nesting**: Use guard clauses and early returns to avoid deep indentation trees.

## Step 7: Handle Edge Cases

A strong candidate is distinguished by how thoroughly they identify and mitigate failure scenarios, boundary conditions, and concurrency hazards.

### A. Core Edge Cases & Failure Scenarios

- **Concurrency & Race Conditions**: What happens when two users attempt to book the exact same parking slot or seat simultaneously?
- **State Inconsistencies**: What happens if the database write succeeds but the payment confirmation email fails to send?
- **Partial Network Failures**: What happens if an external payment gateway charges the card but network drops before returning a 200 OK?
- **Resource Exhaustion**: How does the system respond when all parking slots are filled or memory buffers reach capacity?

### B. Mitigation Strategies

```
  Edge Case Hazard                 Architectural Mitigation
  ─────────────────────────────────────────────────────────────────────────────
  Race conditions             ───> Distributed Locks (Redis) / Optimistic Locking (@Version)
  Duplicate submissions       ───> Idempotency Keys (UUID headers in requests)
  External API outages        ───> Circuit Breakers & Fallback Queues
  Data inconsistency          ───> Two-Phase Commits / Sagas / Compensating Transactions
  Stale cache reads           ───> Cache-Aside with Write-Through Invalidation & TTLs
```

1. **Concurrency Control**: Use synchronized blocks, `ReentrantLock`, or database row-level locking (pessimistic vs. optimistic locking) to prevent double-booking.
2. **Idempotency**: Require unique idempotency tokens for financial transactions so retries do not result in duplicate charges.
3. **Graceful Degradation**: Fall back to cached content or queued processing when downstream dependencies fail.

## Step 8: Class Diagram and Package Structure

Toward the final third of the interview, formalize your design into a structured UML class diagram and a logical directory/package structure.

### A. Class Diagram Checklist
- Display abstract classes and interfaces clearly.
- Include visibility modifiers (`+` public, `-` private, `#` protected).
- Specify accurate relationship notation:
  - **Inheritance** (is-a): Solid line with a hollow triangle arrow.
  - **Interface Realization** (implements): Dashed line with a hollow triangle arrow.
  - **Composition** (owns completely): Solid line with a filled diamond.
  - **Aggregation** (has-a, independent lifecycle): Solid line with a hollow diamond.
  - **Association** (uses): Solid line with an open arrow.

### B. Package Organization

```
com.system.parkinglot/
│
├── controller/          # Request entry points (REST / CLI / Event Listeners)
│   └── ParkingLotController.java
│
├── service/             # Business logic & orchestration
│   ├── ParkingLotService.java
│   └── impl/
│       └── ParkingLotServiceImpl.java
│
├── strategy/            # Pluggable algorithms (Strategy Pattern)
│   ├── SlotAllocationStrategy.java
│   ├── NearestFirstAllocationStrategy.java
│   └── PricingStrategy.java
│
├── model/               # Domain entities, value objects, and enums
│   ├── Vehicle.java
│   ├── ParkingSlot.java
│   ├── Ticket.java
│   └── enums/
│       ├── VehicleType.java
│       └── SlotStatus.java
│
├── repository/          # Persistence abstraction (DAO / Repository)
│   ├── SlotRepository.java
│   └── TicketRepository.java
│
└── exception/           # Custom domain exceptions
    ├── SlotUnavailableException.java
    └── InvalidTicketException.java
```

## Step 9: Discuss Future Add-ons

Conclude the design session by proactively highlighting how your architecture accommodates future feature extensions and scaling requirements without necessitating rewrites.

### Areas to Proactively Discuss
- **Pluggable Third-Party Extensions**: How new payment providers, map engines, or hardware scanners plug in via the existing Strategy or Adapter interfaces.
- **Horizontal Scaling & Performance**: Adding multi-level caches (Caffeine + Redis), asynchronous messaging (Kafka), or database read replicas.
- **Advanced Capabilities**: Introducing analytics, dynamic ML-driven pricing, multi-tenant billing, or geofenced promotions.

## FAQs & Common Doubts

### 1. How much detail should I go into?
> **Answer**: Start broad, then go deep upon interviewer cue. Spend the first 15 minutes establishing requirements, entities, and high-level class structures. Once the interviewer validates the foundation, drill down into specific method signatures, data structures, and concurrency protections for the hero use cases.

### 2. Should I write production-ready code during the discussion?
> **Answer**: Not unless explicitly requested. In most LLD interviews, clean pseudocode, class interfaces, and method signatures with well-defined types are preferred over boilerplate getters, setters, and imports. Prioritize design clarity, pattern application, and data flow over compilation perfection.

### 3. How much business logic should I implement?
> **Answer**: Implement full logic for the **hero use cases** (e.g., the slot allocation algorithm or checkout sequence). For supporting tasks (e.g., hashing a password or sending an email), mock or delegate them to a utility class or service interface.

### 4. How do I decide which design pattern to use?
> **Answer**: Let the problem dictate the pattern, not vice versa:
> - Need dynamic pricing? $\rightarrow$ **Strategy Pattern**.
> - Need flexible object instantiation? $\rightarrow$ **Factory Pattern**.
> - Need event broadcasts to multiple handlers? $\rightarrow$ **Observer Pattern**.
> - Need to wrap legacy or third-party APIs? $\rightarrow$ **Adapter Pattern**.

### 5. What are interviewers primarily evaluating?
> **Answer**: Interviewers grade candidates along four pillars:
> 1. **Problem Scoping & Communication**: Did you ask the right questions and clarify edge cases?
> 2. **Object-Oriented Design & SOLID**: Is the system modular, loosely coupled, and extensible?
> 3. **Design Pattern Mastery**: Did you select and justify appropriate design patterns?
> 4. **Resilience & Concurrency**: Did you account for multi-threading, race conditions, and network failures?
