## Introduction

In a multithreaded environment, ensuring that shared resources are accessed safely is critical. But not every synchronization mechanism is designed to handle real-world constraints effectively. When it comes to designing scalable and responsive systems, certain limitations begin to surface.

### Problem Statement

Let's consider a real-world scenario from BookMyShow. Suppose a user begins booking a movie ticket, and this booking operation runs inside a thread. However, midway through the booking process, the user goes idle - maybe they switch tabs or walk away from the screen.

If the operation continues while holding a monitor acquired using Java's `synchronized` keyword, other threads trying to access the same seat must wait until the owning thread leaves the synchronized section. If the critical section contains long-running or idle work, this can become a serious bottleneck.

In a real application, a lock should normally protect only the short operation that checks and updates the shared seat state. It should not be held while waiting for user input, network calls, or payment processing.

### Why Not Just Rely on synchronized?

- **No timeout support:** A thread cannot specify how long it is willing to wait to enter a synchronized block.
- **No non-blocking acquisition:** There is no monitor equivalent of `tryLock()`.
- **Not interruptible:** A thread waiting to enter a synchronized block cannot be interrupted.
- **No fairness guarantee:** Some threads may wait longer than others.

The `synchronized` keyword remains suitable for many short and straightforward critical sections. When an application needs timed, interruptible, non-blocking, or optionally fair lock acquisition, `ReentrantLock` provides more control.

Before we explore it, we first need to understand the difference between a Lock and a Mutex.

---

## Lock vs Mutex

| Feature / Aspect | Lock | Mutex |
| :--- | :--- | :--- |
| **Definition** | A general synchronization mechanism used to control access to a shared resource. | A specific type of lock used to achieve mutual exclusion, allowing only one thread to access a resource at a time. |
| **Ownership Enforcement** | A lock may or may not enforce ownership depending on its implementation. In Java, both `synchronized` and `ReentrantLock` are ownership-bound. | A mutex follows ownership semantics, meaning only the thread that acquired it may release it. |
| **Java Release Behavior** | In Java, a monitor acquired using `synchronized` is automatically released when the owning thread exits the synchronized block or method. | In Java, `ReentrantLock` behaves like a mutex because only the owning thread can call `unlock()` successfully. |
| **Scope & Variety** | Locks are a broader concept and can include monitors, reentrant locks, read-write locks, spin locks, and other synchronization mechanisms. | A mutex focuses on exclusive ownership: one thread enters the critical section while other threads wait. |
| **Real-Life Analogy** | A general access-control system, like a door lock used to protect a room. | A key-based room where only the person who took the key is allowed to return it. |

## ReentrantLock - A More Flexible Alternative to synchronized

A thread waiting to enter a synchronized block cannot specify a timeout or perform an immediate non-blocking attempt.

This is where `ReentrantLock` provides finer and more explicit control over lock acquisition and release.

### What is ReentrantLock?

`ReentrantLock`, from `java.util.concurrent.locks`, is a mutual-exclusion lock with ownership semantics. The thread that acquires it is the only thread allowed to release it.

The same thread may acquire the lock multiple times without deadlocking itself, which is why the lock is called reentrant. Every successful acquisition must be matched by a corresponding call to `unlock()`.

### When Should You Use It?

| Use Case | Why ReentrantLock Helps |
| :--- | :--- |
| **Explicit control over locking and unlocking** | You can decide exactly when to acquire and release the lock, unlike `synchronized`, which is block-scoped. |
| **Immediate or timed acquisition** | `tryLock()` performs an immediate attempt, while `tryLock(long, TimeUnit)` waits for a limited duration. |
| **Interruptible lock acquisition** | `lockInterruptibly()` allows a waiting thread to respond to interruption. |
| **Optional fairness** | `new ReentrantLock(true)` requests a fairer first-in-first-out acquisition policy under contention. |

### Code Walk-through

Below is a simplified ticket-booking example that replaces `synchronized` with `ReentrantLock`:

```java
import java.util.concurrent.locks.ReentrantLock;

class TicketBooking {
    private int availableSeats = 1;
    private final ReentrantLock lock = new ReentrantLock();

    public void bookTicket(String user) {
        System.out.println(user + " is trying to book...");
        lock.lock();
        try {
            System.out.println(user + " acquired the lock.");
            if (availableSeats > 0) {
                availableSeats--;
                System.out.println(user + " successfully booked the ticket.");
            } else {
                System.out.println(user + " could not book. No seats left.");
            }
        } finally {
            System.out.println(user + " is releasing the lock.");
            lock.unlock();
        }
    }
}

public class Main {
    public static void main(String[] args) throws InterruptedException {
        TicketBooking bookingSystem = new TicketBooking();
        Thread user1 =
                new Thread(() -> bookingSystem.bookTicket("User 1"));
        Thread user2 =
                new Thread(() -> bookingSystem.bookTicket("User 2"));

        user1.start();
        user2.start();

        user1.join();
        user2.join();
    }
}
```

### Key Points

- `lock.lock()` - blocks the calling thread until it obtains exclusive access.
- `lock.unlock()` - must be called by the owning thread.
- The call to `unlock()` belongs in a `finally` block so that the lock is released even if the critical section throws an exception.

Using `ReentrantLock` does not make an already-owned lock expire automatically. Timed methods control how long a waiting thread waits to acquire the lock; they cannot remove the lock from its current owner. Handling an idle owner therefore requires cooperative cancellation, as discussed next.

## Cooperative Lock Expiry: Signalling the Owner to Release

A `ReentrantLock` cannot be forcibly released by a scheduler thread. Only the thread that acquired the lock may call `unlock()`.

For example, suppose an idle user owns the lock and a scheduled task runs after three seconds. The scheduled task runs on the scheduler's own thread, not on the idle user's thread. Consequently:

- `lock.isHeldByCurrentThread()` returns `false` inside the scheduler task.
- Calling `lock.unlock()` from the scheduler throws `IllegalMonitorStateException`.
- Updating a separate boolean flag does not change the actual ownership state of the lock.

The safe approach is **cooperative cancellation**. The scheduler signals or interrupts the owning thread. The owner observes that request, stops its work, and releases the lock from its own `finally` block.

The following example uses interruption because `Thread.sleep()` is interruptible. The scheduler interrupts the idle owner after three seconds. The scheduler never calls `unlock()`.

```java
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.ScheduledFuture;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

class CooperativeTimedLock {
    private final ReentrantLock lock = new ReentrantLock();

    private final ScheduledExecutorService scheduler =
            Executors.newSingleThreadScheduledExecutor();

    public boolean tryLock() {
        return lock.tryLock();
    }

    public ScheduledFuture<?> scheduleCancellation(
            Thread owner,
            long timeoutMillis
    ) {
        return scheduler.schedule(() -> {
            System.out.println(
                    "Timeout reached - interrupting the owner."
            );

            // This is only a cancellation request.
            // The scheduler does not unlock the ReentrantLock.
            owner.interrupt();
        }, timeoutMillis, TimeUnit.MILLISECONDS);
    }

    public void unlockByOwner() {
        if (!lock.isHeldByCurrentThread()) {
            throw new IllegalMonitorStateException(
                    "Only the owning thread may unlock."
            );
        }

        lock.unlock();

        System.out.println(
                "Lock released by " +
                Thread.currentThread().getName()
        );
    }

    public void shutdown() {
        scheduler.shutdownNow();
    }
}

public class Main {
    public static void main(String[] args)
            throws InterruptedException {

        CooperativeTimedLock timedLock =
                new CooperativeTimedLock();

        Thread idleUser = new Thread(() -> {
            if (!timedLock.tryLock()) {
                System.out.println(
                        "IdleUser could not acquire the lock."
                );
                return;
            }

            ScheduledFuture<?> timeoutTask =
                    timedLock.scheduleCancellation(
                            Thread.currentThread(),
                            3000
                    );

            try {
                System.out.println(
                        "IdleUser acquired the lock and is now idle."
                );

                // Simulates interruptible work lasting 5 seconds.
                Thread.sleep(5000);

                System.out.println(
                        "IdleUser completed before the timeout."
                );
            } catch (InterruptedException e) {
                System.out.println(
                        "IdleUser observed the timeout request."
                );

                // Restore the interrupt status after handling it.
                Thread.currentThread().interrupt();
            } finally {
                // Prevent a pending timeout from affecting later work.
                timeoutTask.cancel(false);

                // Executed by IdleUser, the actual lock owner.
                timedLock.unlockByOwner();
            }
        }, "IdleUser");

        Thread activeUser = new Thread(() -> {
            try {
                Thread.sleep(1000);

                while (!timedLock.tryLock()) {
                    System.out.println(
                            "ActiveUser still waiting..."
                    );
                    Thread.sleep(1000);
                }

                try {
                    System.out.println(
                            "ActiveUser acquired the lock and booked!"
                    );
                } finally {
                    // Executed by ActiveUser, which owns the lock here.
                    timedLock.unlockByOwner();
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "ActiveUser");

        idleUser.start();
        activeUser.start();

        idleUser.join();
        activeUser.join();

        timedLock.shutdown();
    }
}
```

### Key Methods Used

- `lock.tryLock()` - attempts to acquire the lock immediately. It returns `true` if successful and `false` otherwise.
- `owner.interrupt()` - sends a cooperative cancellation request to the owning thread. It does not release the lock.
- `lock.isHeldByCurrentThread()` - checks whether the thread executing the method currently owns the lock.
- `lock.unlock()` - releases the lock and may only be called by the owning thread.
- `ScheduledFuture.cancel(false)` - cancels a pending timeout task without interrupting the scheduler thread if the owner finishes normally.

### Key Takeaways

- **No forced expiry:** A scheduler thread cannot forcibly release a `ReentrantLock` owned by another thread.
- **Interruption is a request:** Calling `interrupt()` does not automatically terminate a thread or release its locks.
- **The owner must cooperate:** The owning thread must respond to interruption, leave the critical section, and execute `unlock()` in its `finally` block.
- **Actual release matters:** Other threads can acquire the lock only after the owner calls `unlock()`, not merely when the timeout is reached.
- **Interruption has limitations:** If the owner performs non-interruptible work or ignores interruption, it may continue holding the lock.
- **Avoid unrelated state flags:** A separate `isLocked` flag can become inconsistent with the real state of the `ReentrantLock`.

## Using tryLock(timeout, unit): Timed Wait with an Escape Hatch

In the previous example, `lock.tryLock()` performed a one-shot attempt that either succeeded or failed immediately.

But what if a thread is willing to wait for a short duration without blocking forever? That is exactly what `tryLock(long timeout, TimeUnit unit)` provides.

### Code Demo - Ticket Booking with a 2-second timeout

```java
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

class TicketBookingTryLock {
    private int availableSeats = 1;
    private final ReentrantLock lock = new ReentrantLock();

    public void bookTicket(String user) {
        System.out.println(user + " is trying to book...");
        boolean lockAcquired = false;
        try {
            lockAcquired =
                    lock.tryLock(2, TimeUnit.SECONDS);
            if (!lockAcquired) {
                System.out.println(
                        user +
                        " could not acquire the lock. Try again later."
                );
                return;
            }
            System.out.println(user + " acquired the lock.");
            if (availableSeats > 0) {
                availableSeats--;
                System.out.println(
                        user + " successfully booked the ticket."
                );
            } else {
                System.out.println(
                        user + " could not book. No seats left."
                );
            }
            // Used only to demonstrate the timeout behavior.
            Thread.sleep(3000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            System.out.println(
                    user + " was interrupted while waiting or working."
            );
        } finally {
            if (lockAcquired) {
                System.out.println(
                        user + " is releasing the lock."
                );
                lock.unlock();
            }
        }
    }
}

public class Main {
    public static void main(String[] args)
            throws InterruptedException {
        TicketBookingTryLock booking =
                new TicketBookingTryLock();

        Thread user1 = new Thread(
                () -> booking.bookTicket("User 1")
        );
        Thread user2 = new Thread(() -> {
            try {
                Thread.sleep(500);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
            booking.bookTicket("User 2");
        });

        user1.start();
        user2.start();

        user1.join();
        user2.join();
    }
}
```

### Understanding

- `tryLock(long timeout, TimeUnit unit)` waits up to the specified duration for the lock. It returns `true` if acquisition succeeds and `false` if the timeout expires.
- The method throws `InterruptedException` if the waiting thread is interrupted.
- `TimeUnit.SECONDS` expresses the timeout unit without manual conversion.

### Key Takeaways

- **Timed Wait:** `tryLock(2, TimeUnit.SECONDS)` waits for no more than two seconds.
- **Graceful Fallback:** If acquisition fails, the thread can retry, return an error, or take another path.
- **Acquisition timeout only:** This method limits how long the caller waits. It does not expire a lock already owned by another thread.
- **Safe Release:** Call `unlock()` only when `lockAcquired` is `true`.

## Read-Write Locks

When a data structure is read-heavy, such as stock quotes, configuration caches, or product catalogs, blocking every reader while one writer updates a value wastes parallelism.

`ReadWriteLock` provides two related locks:
- **Read lock:** multiple threads may hold it simultaneously as long as no thread owns the write lock.
- **Write lock:** exclusive access that blocks other readers and writers.

### Real-life Analogy

Think of a public library:
- Visitors may read books simultaneously without disturbing one another.
- When the librarian must update or re-shelve a book, the aisle is temporarily closed to both readers and other librarians.

### Code: Live Stock Price Feed

```java
import java.util.concurrent.locks.ReadWriteLock;
import java.util.concurrent.locks.ReentrantReadWriteLock;

class StockData {
    private double price = 100.0;
    private final ReadWriteLock lock =
            new ReentrantReadWriteLock();

    public void updatePrice(double newPrice) {
        lock.writeLock().lock();
        try {
            System.out.printf(
                    "%s updating price to %.2f%n",
                    Thread.currentThread().getName(),
                    newPrice
            );
            price = newPrice;
        } finally {
            lock.writeLock().unlock();
        }
    }

    public double readPrice() {
        lock.readLock().lock();
        try {
            System.out.printf(
                    "%s read price: %.2f%n",
                    Thread.currentThread().getName(),
                    price
            );
            return price;
        } finally {
            lock.readLock().unlock();
        }
    }
}
```

### Key Takeaways

- **Separate Read and Write Access:** Readers use `readLock()`, while writers use `writeLock()`.
- **Multiple Readers:** Multiple threads can read simultaneously when no writer owns the write lock.
- **Exclusive Writers:** A write lock blocks other readers and writers.
- **Thread Safety:** The locks prevent data races involving the shared `price` field.
- **Use Case Fit:** This pattern is useful for read-heavy systems with less frequent updates.
- **Safe Resource Handling:** The `finally` blocks guarantee that acquired locks are released.

## Semaphores

### The Problem

Imagine a scenario where a premium platform like TUF+ allows access from only a limited number of devices per account. Users may try to log in from several devices simultaneously, exceeding this policy.

### Real World Analogy

Think of a token system at the entrance of a private club. The club has exactly $N$ tokens. Anyone who wishes to enter must take one token and return it when leaving. If no tokens remain, a new visitor must wait or leave. This ensures that no more than $N$ people enter simultaneously.

### The Solution

A Java `Semaphore` maintains a number of permits. A thread acquires a permit before proceeding and releases it after completing its task. If no permit is available, the thread can wait, perform a timed wait, or fail immediately.

Unlike `ReentrantLock`, a semaphore does not track which thread owns a permit. One thread may therefore release a permit acquired by another thread. This can support cross-thread signalling, but every successful acquisition must still be matched by exactly one release.

### Code: Limiting Concurrent Device Logins

```java
import java.util.concurrent.Semaphore;

class TUFPlusAccount {
    private final Semaphore deviceSlots;

    public TUFPlusAccount(int maxDevices) {
        this.deviceSlots = new Semaphore(maxDevices);
    }

    public boolean login(String user) {
        System.out.println(user + " trying to log in...");
        if (deviceSlots.tryAcquire()) {
            System.out.println(
                    user + " successfully logged in."
            );
            return true;
        }
        System.out.println(
                user + " denied login - too many devices."
        );
        return false;
    }

    public void logout(String user) {
        System.out.println(user + " logging out.");
        deviceSlots.release();
    }
}

public class Main {
    public static void main(String[] args)
            throws InterruptedException {
        TUFPlusAccount account =
                new TUFPlusAccount(2);

        Thread user1 = new Thread(
                () -> trySession(account, "User-A")
        );
        Thread user2 = new Thread(
                () -> trySession(account, "User-B")
        );
        Thread user3 = new Thread(
                () -> trySession(account, "User-C")
        );

        user1.start();
        user2.start();
        Thread.sleep(100);
        user3.start();

        user1.join();
        user2.join();
        user3.join();
    }

    private static void trySession(
            TUFPlusAccount account,
            String user
    ) {
        if (!account.login(user)) {
            return;
        }
        try {
            Thread.sleep(500);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            // Release only after a successful login.
            account.logout(user);
        }
    }
}
```

### Key Semaphore Methods

- `tryAcquire()`: Attempts to acquire a permit immediately and returns `true` or `false`.
- `tryAcquire(timeout, unit)`: Waits for a permit for a limited duration.
- `acquire()`: Waits until a permit is available or the thread is interrupted.
- `release()`: Returns a permit. A semaphore does not require the releasing thread to be the thread that acquired it.

### Key Takeaways

- **Fixed-size gate:** Only $N$ simultaneous sessions are allowed.
- **Fairness option:** `new Semaphore(n, true)` enables a fairer queued acquisition policy.
- **Blocking and non-blocking methods:** Choose `acquire()`, `tryAcquire()`, or timed `tryAcquire()` according to the required behavior.
- **No ownership:** Any thread may call `release()`, making semaphores useful for cross-thread signalling and resource pools.
- **Balance acquisitions and releases:** A missing release leaks a permit, while an extra release incorrectly increases the available permit count.

### Use Cases

- Database Connection Pools
- Limiting Concurrent API Requests
- Parking Lot Capacity
- Concurrent Task Execution

These scenarios require precise concurrency limits, which semaphores handle better than basic exclusive locks.

## Comparing Monitors, Reentrant Locks, and Semaphores

The following table compares three core concurrency tools in Java:

| Feature | Monitor (`synchronized`) | `ReentrantLock` | `Semaphore` |
| :--- | :--- | :--- | :--- |
| **Type** | Intrinsic monitor | Explicit Lock API | Permit-based access |
| **Concurrency Limit** | One owning thread | One owning thread | Up to $N$ permits |
| **Reentrant** | Yes | Yes | Not ownership-based |
| **Immediate Acquisition Attempt** | No | Yes, with `tryLock()` | Yes, with `tryAcquire()` |
| **Timed Acquisition** | No | Yes, with timed `tryLock()` | Yes, with timed `tryAcquire()` |
| **Wait/Notify Mechanism** | `wait()` / `notify()` | `Condition.await()` / `signal()` | Permit availability |
| **Ownership Semantics** | Thread-bound | Thread-bound | No thread ownership |
| **Can Another Thread Release It?** | No | No | Yes |
| **Best Use Case** | Simple mutual exclusion | Flexible exclusive locking | Limiting concurrent access |
| **Example Use Case** | Protecting a shared counter | Ticket booking with timed acquisition | Database connection pool |

This comparison helps clarify when to use each mechanism:
- Use **monitors** for straightforward mutual exclusion and thread coordination.
- Use **ReentrantLock** when you need timed acquisition, interruptible waiting, optional fairness, or multiple condition variables.
- Use **Semaphore** when you need to control the number of concurrent operations or intentionally support cross-thread permit release.

Each primitive is powerful when used in the right scenario. Understanding their ownership rules is essential for safe and scalable concurrent code.

## Conclusion

Monitors, reentrant locks, read-write locks, and semaphores all support safe coordination in concurrent programs, but they do not have identical ownership rules.

A `ReentrantLock` cannot be forcibly released by a timeout or scheduler thread. Timed `tryLock()` limits how long a waiting thread waits to acquire the lock; it does not expire a lock already held by another thread. When a running operation must stop after a deadline, the owner must cooperate by responding to interruption or another cancellation signal and then releasing the lock from its own `finally` block.

A semaphore is different because it manages permits rather than thread ownership. This allows cross-thread release, but acquisitions and releases must still be balanced carefully.

Synchronization is infrastructure. It prevents threads from corrupting shared state, preserves consistency, and allows concurrent systems to remain reliable as they scale.

## Summary

| Concept / Primitive | Key Characteristics | Common Use Cases |
| :--- | :--- | :--- |
| **`synchronized` (Monitor)** | Intrinsic, block-scoped, non-timed, non-interruptible, thread-owned | Simple critical sections, protecting counters, basic thread safety |
| **Lock vs Mutex** | Lock is general access control; Mutex enforces strict mutual exclusion and thread ownership | Foundational synchronization theory and architecture |
| **`ReentrantLock`** | Explicit lock API, reentrant, ownership-bound, supports timed/interruptible/fair acquisition | Ticket booking, fine-grained lock boundaries, timeout attempts |

| **`ReadWriteLock`** | Shared read locks for multiple concurrent readers; exclusive write lock for single writer | Cache reads, stock price feeds, configuration readers |
| **`Semaphore`** | Permit counter, non-ownership-bound, cross-thread release capability | Connection pools, API rate limiting, concurrent session gates |
