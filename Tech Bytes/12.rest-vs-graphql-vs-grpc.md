# REST vs GraphQL vs gRPC — Choosing the Right API Style

> REST uses standard HTTP verbs and URLs for simplicity, GraphQL lets clients ask for the exact JSON shape they need in one trip, and gRPC uses compact binary messages over HTTP/2 for ultra-fast service-to-service communication.

## What You'll Learn

- How **REST**, **GraphQL**, and **gRPC** work at a high level
- What **over-fetching** and **under-fetching** mean in REST
- Why **gRPC** with Protocol Buffers is dramatically faster than JSON APIs
- Trade-offs and when to choose each API style in real projects

---

## 1. REST (Representational State Transfer)

**REST** is the classic web API style built directly around HTTP concepts:

- **Resources** are nouns in URLs (`/users/42`, `/orders/99`).
- **Actions** are HTTP methods (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`).
- **Payloads** are usually human-readable JSON.

```http
GET /api/users/42
```

### The REST Catch: Over-Fetching & Under-Fetching

- **Over-fetching:** `/users/42` returns 30 fields when your mobile screen only needs `name` and `avatarUrl`.
- **Under-fetching (N+1 calls):** To render a profile page, you call `/users/42`, then `/users/42/posts`, then `/users/42/followers` — 3 separate round-trips.

**Why REST still dominates:** Dead simple, human-readable, works everywhere, and gets **HTTP caching** (`ETag`, `Cache-Control`, CDNs) for free.

---

## 2. GraphQL (Ask for Exactly What You Need)

Created by Facebook (Meta) in 2012, **GraphQL** exposes a **single endpoint** (usually `POST /graphql`) backed by a strongly typed schema. The client sends a query describing the exact fields it wants:

```graphql
query {
  user(id: "42") {
    name
    avatarUrl
    posts(limit: 3) {
      title
    }
  }
}
```

The server responds with JSON matching that exact shape — no extra fields, no extra round-trips!

### Trade-Offs of GraphQL

- **Pros:** Zero over-fetching/under-fetching, strongly typed schema, great when web/iOS/Android clients each need different slices of the same data.
- **Cons:** Harder HTTP caching (everything is `POST`), complex server-side **N+1 database query** risks (requires DataLoader), and steep overhead for simple CRUD APIs.

---

## 3. gRPC (High-Performance Binary RPC)

Created by Google, **gRPC** treats remote API calls like calling a local function. Instead of sending verbose JSON text over HTTP/1.1, gRPC uses:

- **Protocol Buffers (Protobuf):** A compact binary serialization format defined in a `.proto` contract file.
- **HTTP/2:** Multiplexed streams, header compression, and built-in **bi-directional streaming**.

```protobuf
syntax = "proto3";

service UserService {
  rpc GetUser (UserRequest) returns (UserResponse);
}

message UserRequest {
  int64 id = 1;
}

message UserResponse {
  string name = 1;
  string email = 2;
}
```

Because Protobuf is binary and schema-driven, gRPC payloads are typically **3×–10× smaller and faster** to serialize/deserialize than JSON — and client/server code can be auto-generated in Java, Go, Python, Rust, and TypeScript from the same `.proto` file.

### Trade-Offs of gRPC

- **Pros:** Blazingly fast, low bandwidth, strict contracts, native streaming, polyglot code generation.
- **Cons:** Not human-readable in browser DevTools, limited direct browser support (requires `gRPC-Web` or a proxy).

---

## Side-by-Side Comparison

| Feature | REST | GraphQL | gRPC |
| :--- | :--- | :--- | :--- |
| **Data Format** | JSON (text) | JSON (text) | Protocol Buffers (binary) |
| **Transport** | HTTP/1.1 or HTTP/2 | Usually HTTP POST | HTTP/2 |
| **Endpoints** | Multiple resource URLs | Single `/graphql` endpoint | Service/method RPCs |
| **Browser Support** | Native | Native | Needs gRPC-Web proxy |
| **HTTP Caching** | Built-in & easy | Complex | Manual |
| **Streaming** | Limited (SSE / WebSockets) | Subscriptions | Native bi-directional streaming |
| **Performance** | Good | Good | Highest (compact binary) |

---

## Which One Should You Pick?

- **Pick REST** for public APIs, simple CRUD services, and anything that benefits from browser/CDN caching.
- **Pick GraphQL** when multiple frontends (web, mobile, TV) query complex, nested, graph-like data and want rapid UI iteration without backend changes.
- **Pick gRPC** for internal **microservice-to-microservice** communication, low-latency systems, and real-time streaming pipelines.

> [!TIP]
> Many real-world architectures combine them: **REST or GraphQL** at the public edge (browser/mobile → API Gateway) and **gRPC** internally between backend microservices!

---

## Summary

| API Style | Superpower | Best Fit |
| :--- | :--- | :--- |
| **REST** | Simplicity + universal HTTP caching | Public APIs, standard web backends |
| **GraphQL** | Flexible, client-driven queries in 1 round-trip | Complex frontends with varied data needs |
| **gRPC** | Binary speed + strict contracts + streaming | Internal microservices & real-time systems |
